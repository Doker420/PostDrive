# PostDrive — предложения по модернизации, монетизации и оптимизации

Документ по итогам полного аудита кода (`main.py`, `handlers.py` ~4100 строк,
`user.py` ~2900 строк, `sqliter.py` ~1600 строк, `cryptobot.py`, `mirrors.py`).

Приоритеты: **P0** — блокирует коммерческий запуск, **P1** — нужно в первые недели,
**P2** — рост и развитие.

## 1. Блокеры перед коммерческим запуском (P0)

### 1.1. Сессии Telegram лежат в БД открытым текстом — ⏸ ОТЛОЖЕНО по решению владельца

`accounts.session_string` хранится как обычный `TEXT`. Строка сессии Pyrogram — это
**полный доступ к аккаунту пользователя без пароля и без 2FA**. Утечка `database.db`
(бэкап, украденный диск, доступ к серверу, ошибка в правах) = угон всех аккаунтов
всех клиентов разом. Для сервиса, который берёт деньги, это неприемлемый риск.

**Что сделать:** шифровать `session_string` через `cryptography.Fernet` ключом из
переменной окружения (`SESSION_ENCRYPTION_KEY`), которого нет в репозитории и нет в БД.
Миграция прозрачная: при чтении пробуем расшифровать, при неудаче считаем запись
legacy и перешифровываем на лету.

```python
# sqliter.py
from cryptography.fernet import Fernet
_fernet = Fernet(os.environ['SESSION_ENCRYPTION_KEY'])

def _enc(s: str) -> str:
    return _fernet.encrypt(s.encode()).decode()

def _dec(s: str) -> str:
    try:
        return _fernet.decrypt(s.encode()).decode()
    except Exception:
        return s  # legacy-запись, перешифруем при следующем сохранении
```

Дополнительно: отдельный бэкап-ключ, ротация ключей, запрет на `SELECT session_string`
в любых логах и отчётах.

### 1.2. `config.ini` с секретами отслеживается git — ✅ ИСПРАВЛЕНО

`config.ini` указан в `.gitignore`, но **уже находится в индексе git** (`git ls-files`
его показывает), поэтому игнор на него не действует. Сейчас там плейсхолдеры, но
первый же `git commit -a` после локального заполнения отправит боевой токен бота,
`API_HASH` и токен CryptoBot в публичный репозиторий.

**Что сделать:**

```bash
git rm --cached config.ini
cp config.ini config.ini.example   # только плейсхолдеры
git add config.ini.example
```

Боевые значения — только через переменные окружения (`main.py` это уже поддерживает).
Если токены когда-либо коммитились — отозвать их все (BotFather `/revoke`, my.telegram.org,
CryptoBot) и почистить историю через `git filter-repo`.

### 1.3. Оплата подтверждается только ручной кнопкой

`check_payment_callback` срабатывает, лишь когда пользователь сам нажмёт
«Проверить оплату». Если он оплатил и закрыл Telegram — деньги списаны, подписка не
выдана, приходит запрос в поддержку. При росте это главный источник негатива и возвратов.

**Что сделать:** вебхук CryptoBot (`WEBHOOK_DOMAIN` в конфиге уже зарезервирован) +
фоновый reconciliation-воркер, который раз в минуту добирает `active`-инвойсы за
последние 24 часа и выдаёт подписку автоматически. Кнопку оставить как запасной путь.

Начисление партнёрской комиссии (30%) тоже перенести в этот единый обработчик —
сейчас оно живёт внутри callback'а и при вебхучной оплате просто не выполнится.

### 1.4. Нет обработки FloodWait — ✅ СДЕЛАНО

На весь `user.py` — одно упоминание `FloodWait`, и то в комментарии. При массовом
постинге Telegram штатно отдаёт `FloodWait(x)`; без обработки задача падает в
`except Exception`, помечается как сбойная, а аккаунт продолжает долбить API и
уезжает в бан. Это прямая потеря аккаунтов клиента, то есть потеря клиента.

**Что сделать:** единый декоратор на все вызовы Pyrogram.

```python
from pyrogram.errors import FloodWait, SlowmodeWait, PeerFlood, UserBannedInChannel

async def tg_call(coro_factory, *, max_retries=3, account_id=None):
    for attempt in range(max_retries):
        try:
            return await coro_factory()
        except (FloodWait, SlowmodeWait) as e:
            wait = int(getattr(e, 'value', 60))
            if wait > 3600:                      # сутки ждать бессмысленно
                raise
            logging.warning(f"FloodWait {wait}s (acc={account_id}), sleeping")
            await asyncio.sleep(wait + random.uniform(1, 3))
        except PeerFlood:
            # аккаунт под софт-баном — останавливаем задачи и уведомляем владельца
            raise
    raise RuntimeError("max retries exceeded")
```

Плюс: авто-пауза аккаунта при `PeerFlood`/`UserDeactivated`, health-статус аккаунта
в дашборде («тёплый / ограничен / забанен»).

## 2. Оптимизация и надёжность (P1)

### 2.1. Пул соединений к БД — ✅ СДЕЛАНО

Было: один общий `sqlite3.Cursor` на весь процесс. Два конкурентных обработчика
могли выполнить `execute()` и `fetchone()` вперемешку и получить чужие строки.
Воспроизведено на нагрузочном тесте: старый код падает с **SIGBUS** (аварийное
завершение процесса) при 15 параллельных клиентах, новый — 0 ошибок.

Сейчас: LIFO-пул на 12 соединений (`DB_POOL_SIZE`), каждая задача получает своё
соединение и свой курсор через `contextvars`, реентрантно; записи сериализуются
write-локом, чтения идут параллельно благодаря WAL. Все 276 существующих вызовов
`self.c.execute(...)` продолжают работать без правок — метакласс `_PoolBoundMeta`
автоматически оборачивает публичные методы.

### 2.2. Переезд на PostgreSQL — ✅ ПЕРЕКЛЮЧАТЕЛЬ ДОБАВЛЕН

SQLite даже в WAL допускает **только одного писателя одновременно**. При постоянных
записях из задач постинга (статусы, отчёты, прогресс) писатели встанут в очередь по
30-секундному `busy_timeout`. Пул это сгладил, но физический потолок остаётся.

Рекомендация: `asyncpg` + SQLAlchemy Core, БД выносится на отдельный инстанс.
Уровень доступа уже изолирован в `DBConnection`, поэтому миграция затрагивает один файл.
Триггер для переезда — устойчиво >50 записей/сек или >300 одновременно активных задач.

### 2.3. Реальные лимиты памяти на клиентов

`MAX_ACTIVE_CLIENTS = 5000` — это 5000 одновременных Pyrogram-клиентов в памяти
одного процесса. Каждый держит TCP-соединение, криптосессию и буферы: ориентировочно
3–8 МБ, то есть **15–40 ГБ RAM** плюс 5000 сокетов. На практике процесс умрёт по OOM
далеко раньше.

**Что сделать:** снизить дефолт до 200–300 на процесс, а горизонтально масштабировать
воркерами: шардировать аккаунты по `account_id % N` между несколькими процессами,
координация через Redis. `MAX_GLOBAL_TASKS = 5000` снизить синхронно.

### 2.4. Вынести воркеры из процесса бота

Сейчас постинг, парсинг, инвайтинг и нейрокомментинг живут в том же event loop, что и
polling бота. Одна тяжёлая задача (парсинг 50 000 сообщений) добавляет задержку
интерфейсу всем пользователям, а рестарт ради деплоя убивает все активные задачи.

**Что сделать:** разделить на `bot` (только UI) и `worker` (задачи), очередь — Redis
(ARQ или Celery). Плюсы: деплой бота без остановки рассылок, независимое
масштабирование воркеров, переживание рестартов. Таблица `running_tasks` и
`mark_all_running_tasks_interrupted()` уже дают основу для восстановления.

### 2.5. Наблюдаемость

Сейчас диагностика — это `print()` и `logging` в stdout. При платящих клиентах нужно
понимать, сколько сообщений ушло, где FloodWait, какие аккаунты умирают.

Минимум: структурные логи JSON, Sentry на исключения, Prometheus-метрики
(`posts_sent_total`, `floodwait_seconds_total`, `accounts_banned_total`,
`db_pool_in_use` — `pool_stats()` уже отдаёт нужные цифры), алерты в админ-чат.

### 2.6. Тесты

Тестов нет вообще. Для проекта, где ошибка стоит клиенту забаненных аккаунтов,
нужен хотя бы каркас: `pytest` + `pytest-asyncio`, юнит-тесты на `sqliter`
(фильтры типов чатов, пагинация, идемпотентность синка, партнёрские начисления),
мок-тесты на разбор callback_data, нагрузочный тест пула (уже написан в этой ветке).
Плюс GitHub Actions на каждый PR.

## 3. Монетизация (P1–P2)

### 3.1. Проблема текущей модели

Тарифы: 3 дня $3, месяц $15, 3 месяца $35, **навсегда $99**. Ограничение одно —
активна подписка или нет. Отсюда три системные проблемы:

1. **«Навсегда» убивает выручку.** Клиент платит $99 один раз и дальше бесконечно
   потребляет самый дорогой ресурс — прокси, AI-токены, CPU, RAM. Через год такой
   клиент глубоко убыточен. При этом $99 = всего 6.6 месяцев подписки.
2. **Нет апсейла.** Пользователь с 1 аккаунтом и пользователь с 200 аккаунтами
   платят одинаково, хотя нагрузка отличается в 200 раз. Тяжёлые пользователи
   субсидируются лёгкими, а расти внутри тарифа некуда.
3. **AI ничем не ограничен.** Нейрокомментинг ходит в Groq/OpenAI/Gemini; при
   безлимитном тарифе один активный клиент может сжечь месячную выручку в токенах.

### 3.2. Тарифная сетка по лимитам

Перейти от «доступ есть/нет» к квотам. Добавить в `tariffs` поля:
`max_accounts`, `max_tasks`, `ai_comments_per_day`, `parse_per_day`, `has_proxy_pool`.

| Тариф | Цена/мес | Аккаунтов | AI-комментов/сут | Кому |
|---|---|---|---|---|
| Trial | $0, 3 дня | 1 | 20 | Пробуют продукт |
| Starter | $19 | 3 | 200 | Соло-арбитражник |
| Pro | $49 | 15 | 1 500 | Небольшая команда |
| Team | $129 | 50 | 6 000 | Агентство |
| Enterprise | от $299 | от 150 | по договору | Сетки, white label |

Эффекты: средний чек выше текущих $15; понятный путь апгрейда; расходы на AI и прокси
привязаны к цене; бесплатный trial (вместо платного за $3) расширяет верх воронки —
$3 отсекает больше людей, чем приносит денег.

«Навсегда» — убрать из продажи. Существующим владельцам сохранить доступ (иначе репутационный
удар), но зафиксировать лимиты на уровне Pro и не включать туда новые фичи.

### 3.3. Оплата за ресурсы сверх квоты

Продавать пакеты поверх подписки — самый быстрый способ поднять ARPU без роста базы:

- **Слоты аккаунтов**: +$3/мес за аккаунт сверх тарифа.
- **AI-пакеты**: 1 000 комментариев за $5 (себестоимость на Groq — центы).
- **Резидентные прокси**: $2–4/мес за аккаунт, продаём как встроенный сервис.
  Сейчас прокси — головная боль клиента (`parse_proxy_string` есть, а прокси нет);
  это готовая маржинальная услуга, привязывающая клиента к платформе.
- **Прогрев аккаунтов**: автоматический warmup новых сессий, $5–10 за аккаунт.

### 3.4. Биллинг

- **Автопродление.** Сейчас каждый цикл — ручная покупка инвойса, отвал на каждом
  продлении огромный. CryptoBot Subscriptions или напоминания за 3/1 день + 1 день
  грейс-периода вернут заметную часть выручки. Это самая дешёвая в реализации мера с
  прямым влиянием на MRR.
- **Способы оплаты.** Только крипта отсекает часть аудитории — добавить Telegram Stars
  (нативно для TG-аудитории, без KYC) и карты (ЮKassa/Stripe по региону).
- **Годовая подписка** со скидкой ~20% вместо «навсегда»: и деньги вперёд, и не вечное
  обязательство.

### 3.5. Партнёрская программа

Механика на 30% уже есть (`partners`, `partner_referrals`, `add_partner_earning`), но:

- начисление живёт внутри callback оплаты — при вебхуке не сработает (см. 1.3);
- 30% пожизненно на «навсегда» = отрицательная юнит-экономика;
- нет вывода средств, нет статистики, нет защиты от самореферала.

**Что сделать:** 30% на первый платёж и 15% на продления; запрет самореферала по
`user_id`; страница статистики (клики → регистрации → оплаты); авто-вывод от $50
через CryptoBot.

### 3.6. Retention

- **Онбординг**: сейчас новый пользователь попадает в меню из 11 кнопок без подсказок.
  Мастер «подключи аккаунт → выбери группы → запусти первый пост» повышает конверсию
  из trial в оплату сильнее любой скидки.
- **Еженедельный дайджест**: «отправлено 4 812 сообщений, охват 120 групп» — показывает
  ценность перед списанием и снижает отток.
- **Win-back**: через 3 и 14 дней после окончания подписки — промокод на возврат
  (механика промокодов уже реализована).

## 4. Функциональное развитие (P2)

- **Планировщик постов** — по расписанию/дням недели, а не только «интервал N минут».
- **A/B тест креативов** — автоматически сравнивать варианты по отклику; логичное
  развитие уже существующего спинтакса `{вариант1|вариант2}`.
- **Анти-бан автопилот** — адаптивные задержки по реакции API, авто-прогрев, ротация
  аккаунтов; главная боль аудитории и сильнейший дифференциатор.
- **Веб-дашборд** — Telegram-интерфейс неудобен для 50+ аккаунтов; графики, массовые
  операции, роли. Отдельный повод для тарифа Team.
- **Командный доступ** — несколько операторов на один кабинет с правами (тариф Team+).
- **White label** — свой бот под брендом агентства, от $299/мес.
- **API** — интеграция с CRM клиента, тариф Enterprise.

## 5. Порядок внедрения

**Спринт 1 (безопасность и деньги).** Шифрование сессий; вынос `config.ini` из git и
отзыв токенов; вебхук оплаты + reconciliation; обработка FloodWait. Без этих четырёх
пунктов масштабировать продукт опасно: первый же инцидент с угоном аккаунтов или
потерянными платежами обойдётся дороже всей разработки.

**Спринт 2 (устойчивость).** Разделение bot/worker, Redis-очередь, Sentry и метрики,
каркас тестов + CI, снижение лимитов клиентов до реалистичных.

**Спринт 3 (монетизация).** Квоты в тарифах, новая сетка, автопродление, Telegram Stars,
доработка партнёрки.

**Спринт 4 (рост).** Прокси и AI-пакеты как отдельные услуги, онбординг-мастер,
веб-дашборд, планировщик.

**Триггер для PostgreSQL** — устойчиво >50 записей/сек или >300 параллельных задач.

## 7. Как включить PostgreSQL

SQLite остаётся значением по умолчанию — переключение полностью обратимо.

```bash
pip install psycopg2-binary
createdb postdrive
```

```ini
[DATABASE]
ENGINE = postgres
DSN = postgresql://postdrive:password@localhost:5432/postdrive
POOL_SIZE = 20
```

Либо через переменные окружения (приоритетнее конфига):

```bash
export DB_ENGINE=postgres
export DATABASE_URL=postgresql://postdrive:password@localhost:5432/postdrive
```

При старте бот печатает используемую СУБД:
`🗄  DB: PostgreSQL (postgresql://***@localhost:5432/postdrive), pool=20`

**Что делает переключатель.** SQL-запросы транслируются из диалекта SQLite в
PostgreSQL на лету (`dbconfig.translate`): `AUTOINCREMENT` → `BIGSERIAL`,
`strftime('%s','now')` → `EXTRACT(EPOCH FROM NOW())`, `INSERT OR IGNORE` →
`ON CONFLICT DO NOTHING`, плейсхолдеры `?` → `%s`, `PRAGMA` игнорируются.
Строки результата возвращаются объектом, поддерживающим доступ и по имени
(`row['col']`), и по индексу (`row[0]`), как `sqlite3.Row`.

**Важно про миграцию данных.** Переключатель создаёт **пустую** схему в
PostgreSQL. Перенос существующих данных из `database.db` не автоматизирован —
для боевой миграции используйте `pgloader` или выгрузку/загрузку по таблицам,
и обязательно проверьте результат на копии. Рекомендуемый порядок: поднять
PostgreSQL параллельно, перелить данные, сверить количество строк в ключевых
таблицах (`users`, `accounts`, `account_chats`, `invoices`), затем переключить
`ENGINE` и перезапустить бота.

## 8. Обработка FloodWait (реализовано)

### Что было

На весь `user.py` не было ни одного `except FloodWait`. Все 35 вызовов Pyrogram
(`send_message`, `send_photo`, `join_chat`, `add_chat_members`, `invoke`) шли напрямую.
Рассылка ловила ошибку в общий `except Exception`, писала «ошибка» в отчёт и
**продолжала долбить API следующим чатом** — ровно то поведение, за которое
Telegram выдаёт спам-блок, а затем перманентный бан.

### Что стало

**Единая точка защиты — `AccountSessionManager.tg_call()`**. Принимает *фабрику*
корутины (не корутину: повторно ожидать уже выполненную корутину нельзя),
поэтому ретраи безопасны.

| Класс ошибки | Реакция |
|---|---|
| `FloodWait`, `SlowmodeWait` | Спим `wait + 1–3с` джиттера, повторяем. Счётчик пишется в БД |
| `FloodWait` > `MAX_FLOOD_WAIT` (30 мин) | Не ждём. Аккаунт → `restricted`, задача останавливается |
| `PeerFlood`, `UserBannedInChannel` | Аккаунт → `restricted`, инструкция про @SpamBot владельцу |
| `SessionExpired`, `AuthKeyUnregistered`, `UserDeactivatedBan`, … | Аккаунт → `banned`, требуется переподключение |
| `ChatWriteForbidden`, `ChannelPrivate`, `UserPrivacyRestricted`, … | Пропускаем **цель**, аккаунт остаётся здоровым |
| `TimeoutError`, `ConnectionError`, `OSError` | Экспоненциальный бэкофф до 30с |

Имена классов ошибок в Pyrogram меняются между версиями (`FloodPremiumWait`
в 2.0.106 отсутствует), поэтому используется толерантный загрузчик `_err()`:
недостающий класс подменяется заглушкой, которая никогда не выбрасывается.
Апгрейд Pyrogram не уронит бота на `ImportError`.

### Здоровье аккаунта

Шесть новых колонок в `accounts`: `health`, `health_reason`, `restricted_until`,
`flood_count`, `flood_total_seconds`, `last_flood_at`.

- `ok` — норма;
- `cooldown` — активный FloodWait, **истекает сам** при чтении после `restricted_until`;
- `restricted` — спам-блок, нужны действия владельца;
- `banned` — сессия мертва.

Перед запуском рассылки и нейрокомментинга вызывается `is_account_usable()` —
ограниченный аккаунт просто не стартует, с понятной причиной на русском.
В списке аккаунтов статус виден иконкой (⏳ / ⚠️ / 🚫), в панели аккаунта —
причина, остаток кулдауна, статистика лимитов и кнопка «♻️ Сбросить статус».

### Настройка

```ini
[LIMITS]
MAX_FLOOD_WAIT = 1800   ; сколько секунд готовы ждать; дольше — считаем спам-блоком
```
